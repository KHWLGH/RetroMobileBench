# 测试与结果

RetroMobileBench 采用固定测试套件，按下表顺序串行执行 15 个阶段。应用以全自动方式运行固定负载，界面不提供单项选择、线程数、分辨率、轮数或软硬解切换。完整构建流程与资源准备见[开发与构建](development.md)，真机与模拟器测试记录见[验证与限制](validation.md)。

## 测试阶段总览

常规阶段连续运行 3 轮（轮间间隔 1 秒），视频与 GPU 阶段各运行 1 次，阶段之间间隔 1 秒。

| 顺序 | 测试阶段 | 负载配置与主要输出指标 | 轮数 |
|---|---|---|---|
| 1 | CoreMark | 单线程 + 多线程（N 线程）；2000 字节工作区、两套种子，单次计时至少 10 秒；输出 `iterations/s` | 3 |
| 2 | SciMark | 单线程 small 数据集（FFT、SOR、Monte Carlo、Sparse、LU）；种子 101010，单项至少 1500 ms；输出各内核 `MFLOPS` | 3 |
| 3 | zlib 压缩 | zlib 1.3.1，固定 1 MiB 语料、压缩级别 6；单线程 + N 个独立流，压缩与解压各至少 1500 ms；输出 `MB/s` | 3 |
| 4 | 加密与摘要 | Mbed TLS 2.28.10，AES-128-GCM 加密/解密及 SHA-256；每线程 256 KiB 独立缓冲区，单线程 + N 线程，各至少 1500 ms；输出 `MB/s` | 3 |
| 5 | 图片解码 | libjpeg-turbo 2.1.5.1 与 libpng 1.6.43，解码 480p / 720p / 1080p 的 JPEG 与 PNG 共 6 张图片至 RGBA8；输出 `MPix/s`、`ms/张` | 3 |
| 6 | 视频解码与播放 | 7 段固定视频的软件解码吞吐、系统解码吞吐与实时渲染播放，记录状态、帧数、耗时与校验信息 | 1 |
| 7 | 内存带宽与延迟 | 8 MiB C 复制/填充、4 MiB 指针追踪延迟，以及单线程 + N 线程共享 24 MiB 工作集的 Triad 带宽；输出 `MB/s`、`ns` | 3 |
| 8 | 文件存储 | 内部私有目录 4–32 MiB 测试文件；顺序读写块 256 KiB、随机读写块 4 KiB（256 次操作）；输出 `MB/s`、`IOPS` | 3 |
| 9 | SQLite 事务 | SQLite 3.53.1；INSERT / UPDATE / DELETE 各 300 个独立事务（每事务一行 1 KiB，`DELETE` 日志、`FULL` 同步）；输出 `TPS` | 3 |
| 10 | Web 日常响应 | 离线系统 WebView 独立横向全屏窗口；页面构建、待办交互、文本排版、数据展示 4 项各 20 个单元；输出总 `ms`、`ms/单元`（越低越好） | 3 |
| 11 | Egypt HD 离屏 | OpenGL ES 2.0，ETC1 纹理，固定 1920×1080 FBO，时长 113 秒；输出 `frames`、`FPS` | 1 |
| 12 | Egypt HD 屏上 | OpenGL ES 2.0，ETC1 纹理，实际窗口分辨率，时长 113 秒；输出 `frames`、`FPS` | 1 |
| 13 | T-Rex 离屏 | OpenGL ES 2.0，ETC1 纹理，固定 1920×1080 FBO，时长 56 秒；输出 `frames`、`FPS` | 1 |
| 14 | T-Rex 屏上 | OpenGL ES 2.0，ETC1 纹理，实际窗口分辨率，时长 56 秒；输出 `frames`、`FPS` | 1 |
| 15 | Fill 离屏 | OpenGL ES 2.0，ETC1 纹理，固定 1920×1080 FBO，时长 60 秒；输出 `MTexels/s` | 1 |

## 线程调度与计时校验

### 线程配置与计时规则

- **并发线程数（N）**：CoreMark、zlib、加密和内存 Triad 均测试单线程与 N 线程（单核设备自动省去重复的并行轮次）。线程数 N 综合系统的 CPU present、CPU 目录、在线状态及运行时报告确定，仅在缺失拓扑信息时回退至 configured 数量。工作线程上限为 64。
- **计时窗口**：原生层统一使用 `CLOCK_MONOTONIC` 单调时钟。数据预热、已知测试向量检查和结果校验均位于计时窗口之外。
- **系统调度**：测试过程不要求 root 权限，不绑核，也不修改系统调频策略（governor），由系统内核自然管理核心热插拔、线程调度与频率调节。报告中附带的运行前后核心在线数与频率作为环境快照记录。

### 数据正确性校验

- **CPU 与压缩**：CoreMark 使用上游核心源码与自定义 Android 移植层，要求通过两套种子校验及最短运行时间检查；SciMark 对各内核进行独立计时与数值校验；zlib 在计时前后核对压缩与解压还原的数据。
- **加密**：每个工作线程使用独立上下文，在计时外验证 AES/GCM/SHA 已知向量与错误标签拒绝，并在所有线程 `join` 完成后统一校验完整输出，避免校验操作干扰其他仍在计时的线程。
- **图片解码**：计时前将压缩数据载入内存并分配可复用的输出缓冲区，计时范围仅包含 RGBA8 内存解码（不含磁盘读取）。JPEG 采用固定标量 accurate 整数 DCT 与 fancy upsampling，PNG 保留非预乘 RGBA 与透明通道，解码输出会与参考像素及哈希逐一比对。

## 专项测试说明

### 视频解码与播放

视频测试包含 7 段固定素材（均为 30 fps、8-bit YUV420、无音轨），具体编码参数与文件 SHA-256 记录在[固定素材清单](../app/src/main/assets/media/manifest.json)中，素材署名见[许可与分发](licenses.md)。

| 素材 ID | 编码规格 | 分辨率 | 时长 / 帧数 |
|---|---|---|---|
| `h264-sd` | H.264 Baseline level 3.0 | 854×480 | 4 秒 / 120 帧 |
| `h264-hd` | H.264 Baseline level 3.1 | 1280×720 | 4 秒 / 120 帧 |
| `h264-hd-high` | H.264 High（含 CABAC / B 帧） | 1280×720 | 4 秒 / 120 帧 |
| `h264-fhd` | H.264 High | 1920×1080 | 4 秒 / 120 帧 |
| `h263` | H.263 | 352×288 | 1 秒 / 30 帧 |
| `mpeg4` | MPEG-4 Part 2 | 640×480 | 1 秒 / 30 帧 |
| `vp8` | VP8 | 640×480 | 1 秒 / 30 帧 |

每段素材依次通过三条独立路径进行测试，各路径分别记录完成状态（成功、不支持、失败或超时）：

1. **软件解码吞吐**：基于内置 FFmpeg 4.4.6 标量解码器，不按播放帧率节流，解码输出完整 YUV420 帧并校验首帧哈希。计时包含缓存文件读取与解封装。
2. **系统解码吞吐**（API 16+）：通过同步 `MediaCodec` 按规则选择系统解码器（主解码器失败时支持回退一次），检查输出尺寸、PTS、EOS，并对可读的线性颜色布局抽样检查亮度数据。
3. **实时播放**：按 PTS 时间戳节奏向 `Surface` 提交画面，记录解码与提交帧数以及是否低于实时帧率。API 8–15 设备通过 `MediaPlayer` 执行此路径。

针对部分 Android 4.1（API 16–17）设备在解析含 B 帧的 H.264 素材时系统 `MediaExtractor` 返回归零 DTS 的问题，应用会在计时前使用内置 FFmpeg 解封装器核对样本哈希、大小、顺序与时间戳。确认样本一致且原始时间戳异常时，改用容器 PTS 送入 `MediaCodec`；预检过程位于解码计时窗口之外。此外，API 29 及以上版本会额外记录系统声明的解码器软硬件属性。

### Web 日常响应

Web 测试在独立的 `:web` 进程中启动横向全屏系统 WebView，评估 JavaScript、DOM 操作、样式计算与页面布局响应速度。测试内容为项目原创的离线合成页面与数据（生成配方见 [`web-assets.gradle.kts`](../app/web-assets.gradle.kts)，哈希锁定见 [`web-corpus-lock.json`](../app/web-corpus-lock.json)）。

每轮测试前先对 4 个分项各执行 1 个单元的预热、校验与复位，随后各执行 20 个正式工作单元（每轮共 80 个单元）：

| 分项 | 单个工作单元操作 | 每轮工作量（20 单元） |
|---|---|---|
| 页面构建 | 清空后创建 32 张卡片（每卡 8 个元素节点），应用样式并读取布局属性 | 640 张卡片 / 5120 个元素 |
| 待办交互 | 添加 100 项，切换前 50 项状态；依次按 all / active / completed / all 过滤；清空列表 | 添加 2000 项、切换 1000 项、过滤 80 次、删除 2000 项 |
| 文本排版 | 渲染 24 段 × 256 ASCII 字符；替换 48 处短语、高亮 240 个关键词；折叠并展开前 12 段；恢复原状 | 替换 960 处、高亮 4800 处、折叠/展开 240 对 |
| 数据展示 | 解析 1000 条 × 8 字段 JSON；筛选 500 条并排序；渲染前 100 行 × 6 列表格并序列化结果 | 解析 20000 条记录，渲染 2000 行 / 12000 个单元格 |

- **视口与布局**：页面采用 `width=device-width`、固定双列卡片与全宽表格（字号 12 CSS px、行高 18 CSS px、文本缩放 100%），记录实际 CSS 与物理视口尺寸。测试过程中若视口尺寸变化则中断当次测量。
- **计时与控制**：每项从首个正式单元开始计时，至第 20 个单元的任务与布局检查点完成为止（包含单元间的 `setTimeout(0)` 调度开销）。计时优先使用 `performance.now()`，不可用时回退至 `Date.getTime()`。完整结果核对与跨进程通信（通过 `onJsPrompt` 传递）均在停表后进行。
- **超时保护**：主进程设有硬性超时限制（单轮启动/预热 15 秒、单项测试 20 秒、整阶段上限 330 秒），即使页面脚本卡死也可安全取消并回收子进程。

### 内存、存储与 GPU 说明

- **内存带宽与延迟**：Triad 测试复用 STREAM 的 `a = b + 3 * c` 内核，3 个 `double` 数组各占 8 MiB，单线程与多线程共享固定的 24 MiB 工作集，按 64 字节边界划分无重叠区间并运行至少 1500 ms。由于工作集固定，结果会受 CPU 缓存容量与调度策略影响，属于固定工作集的 STREAM 变体测试。8 MiB 内存复制按“读 + 写”总字节数计算带宽。
- **文件存储与 SQLite**：文件存储测试默认使用 32 MiB 文件（空间受限时最低降至 4 MiB，并预留 16 MiB 剩余空间）；写入启用 `O_SYNC`，读取优先尝试 `O_DIRECT`（不支持时标记为 `cached`）。SQLite 测试使用独立构建的 SQLite 3.53.1 操作临时测试库，与保存历史成绩的应用数据库相互独立。
- **GPU 离屏与屏上渲染**：GPU 阶段基于开源 GFXBench 的 OpenGL ES 2.0 场景构建。离屏模式使用小尺寸 pbuffer 配合固定 1080p FBO；屏上模式进入独立横向全屏窗口，创建精确的 `RGB888`（`alpha = 0`、无 MSAA、`depth >= 16`）不透明窗口表面并按实际分辨率渲染。屏上帧率受设备分辨率、VSync 与屏幕刷新率影响，与固定 1080p 离屏成绩分开记录。Fill 场景运行完整 60 秒自适应负载，输出纹理填充率（`MTexels/s`）。
- **GPU 屏上 HUD**：屏上渲染期间，左上角浮层约每秒计算一次成功交换缓冲区的速率（`FPS（提交）`）并读取系统广播的最新电池温度；离屏、Web 与视频阶段不启用该浮层。

## 结果保存与环境监测

测试报告采用分级 JSON 结构：会话级报告记录会话 ID、构建标识、起止时间、整体状态与各阶段结果列表；阶段级报告保存每轮原始样本、配置参数、原生库/ABI 信息及运行环境数据。对于 3 轮制的测试阶段，当 3 轮全部完成且运行参数一致时自动计算有效中位数。

| 状态值 | 含义说明 |
|---|---|
| `completed` | 阶段内所有测试项目正常完成 |
| `partial` | 部分子路径已完成并保留有效结果，部分路径不支持或失败 |
| `unsupported` | 当前设备或系统版本不支持该测试能力 |
| `skipped` | 运行前环境条件（如内存、存储空间）不满足，跳过执行并记录原因 |
| `failed` / `timeout` | 执行或数据校验失败 / 超出规定时限 |
| `cancelled` / `interrupted` | 用户主动取消 / 因切后台、锁屏、窗口丢失或进程重启而中断 |

- **断点保护**：每完成一轮测试立即写入检查点。若应用进程意外重启，启动时会恢复已保存的轮次并将未完成的阶段标记为 `interrupted`。测试结束后支持将当前报告或历史记录复制为 JSON。
- **温度监测**：整次测试共用一个低优先级后台线程，约每 2 秒读取一次系统电池温度广播，记录各阶段的起始温度、结束温度、峰值温度、温升及充电状态。温度数据仅作环境参考，不会触发降频停测或强制冷却等待。
