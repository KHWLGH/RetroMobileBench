# 测试与结果

RetroMobileBench 采用固定测试套件（`fixed-suite-v1`），按下表顺序串行执行 **12 个阶段**。应用专为老旧移动设备评测与横评设计，以全自动方式运行固定负载，界面不提供单项选择、线程数、分辨率、轮数或软硬解切换，并在报告总览页提供一屏展示的「核心指标速览（横评总结）」。完整构建流程与资源准备见[开发与构建](development.md)，真机与模拟器测试记录见[验证与限制](validation.md)。

## 测试阶段总览（12 阶段）

前 6 个常规阶段连续运行 3 轮（轮间间隔 1 秒，取有效中位数），视频与 5 个 GPU 阶段各运行 1 次，阶段之间间隔 1 秒。

| 顺序 | 测试阶段 | 明确测试工作量与主要输出指标 | 轮数 |
|---|---|---|---|
| 1 | CPU 整数（CoreMark®） | 单核 + 多核（N 线程）；2000 字节栈工作区、双套种子校验，每段正式计时至少 10 秒；输出**单核 / 多核 `iterations/s`** | 3 |
| 2 | CPU 浮点（SciMark 2.0） | 单核 + 多核（N 线程）；small 数据集（FFT 1024、SOR 100×100、Monte Carlo 16384、Sparse N=1000/nz=5000、LU 100×100），每内核至少 1000 ms；输出**单核综合 / 多核综合 `MFLOPS`**（五项算术均值）及各内核明细 | 3 |

| 7 | 视频解码与播放 | **7 段固定视频**（240p H.263、360p MPEG-4、480p/720p/1080p H.264、720p VP8/VP9）依次执行 FFmpeg 标量软解、MediaCodec 系统解码与 Surface 实时播放 | 1 |

## 线程调度与计时校验

### 线程配置与计时规则

- **并发线程数（N）**：CoreMark、SciMark 2.0 和内存 Triad 均测试单线程与 N 线程（单核设备自动省去重复的并行阶段）。线程数 N 综合系统的 CPU present、CPU 目录、在线状态及运行时报告确定，仅在缺失拓扑信息时回退至 configured 数量。工作线程上限为 64。
- **计时窗口**：原生层统一使用 `CLOCK_MONOTONIC` 单调时钟。数据预热、已知测试向量检查和结果校验均位于计时窗口之外。
- **系统调度**：测试过程不要求 root 权限，不绑核，也不修改系统调频策略（governor），由系统内核自然管理核心热插拔、线程调度与频率调节。报告中附带的运行前后核心在线数与频率作为环境快照记录。

### 数据正确性校验

- **CPU 整数（CoreMark®）**：使用上游核心源码与自定义 Android 移植层，要求通过两套种子（validation + performance）CRC 校验及每段至少 10 秒正式运行时间检查。
- **CPU 浮点（SciMark 2.0）**：在单核与多核（每线程独立工作缓冲区）阶段分别运行 FFT（1024）、SOR（100×100）、Monte Carlo（16384）、稀疏矩阵乘法（N=1000, nz=5000）与 LU 分解（100×100），计时外核对数值残差与积分精度，并汇总输出单核与多核综合 MFLOPS（五项算术平均值）。

## 专项测试说明

### 内存、存储与 SQLite 测试量说明

1. **内存带宽与延迟（`memory-tiny-v1`）**：
   - **8 MiB 复制与填充**：分配两个 8 MiB 缓冲区（共 16 MiB），C 语言 `aligned_block_copy` 按“8 MiB 读 + 8 MiB 写 = 16 MiB/次”计算有效带宽，`aligned_block_fill` 按“8 MiB 写/次”计算带宽。
   - **4 MiB 随机指针链延迟**：在 4 MiB 连续空间内构建覆盖全部 **1,048,576 个节点（100 万节点）** 的单向伪随机循环指针链，每次操作追踪 4096 步依赖访问，反映 L2/TLB 穿透后的真实 DRAM 访问延迟（`ns`）。
   - **24 MiB 共享 Triad 带宽**：复用 STREAM 的 `a[i] = b[i] + 3.0 * c[i]` 内核，3 个 `double` 数组各占 8 MiB（共 1,048,576 个元素，总工作集固定 **24 MiB**）。单线程与多线程共享该 24 MiB 工作集，按 64 字节缓存行边界划分无重叠区间，每项运行至少 1500 ms。

2. **存储读写测试（`storage-file-v1`）**：
   - **32 MiB 测试文件**：默认在应用内部缓存目录创建 **32 MiB** 测试文件（当剩余空间不足时在 4–32 MiB 间自适应，并强制预留至少 16 MiB 可用空间）。
   - **顺序读写（256 KiB × 128 块）**：以 256 KiB 对齐块顺序写满整个测试文件并调用 `fsync`（`O_SYNC`），随后顺序读回全部数据并逐块校验内容（MB/s）。
   - **随机读写（4 KiB × 256 次）**：按固定伪随机偏移序列执行 256 次 4 KiB 随机覆写（`O_SYNC` 每次落盘）与 256 次 4 KiB 随机读取校验（IOPS）。读取阶段优先启用 `O_DIRECT` 绕过页缓存，内核不支持时回退并记录为 `cached`。

3. **SQLite 事务测试（`sqlite-tps-v1`）**：
   - **900 次独立同步事务**：使用内置 SQLite 3.53.1 创建独立测试库，依次执行 **300 次独立 `INSERT` 事务**、**300 次独立 `UPDATE` 事务**、**300 次独立 `DELETE` 事务**（每事务仅操作 1 行并立即 `COMMIT`，共 **900 次落盘提交**）。
   - **行载荷与落盘策略**：每行包含 **1024 B（1 KiB）** 确定性文本载荷与整型校验列；数据库页大小固定为 **4096 B（4 KiB）**，页缓存上限 2000 KiB，启用 `journal_mode = DELETE` 与 `synchronous = FULL`，并在 `UPDATE` 与 `DELETE` 阶段间核对表行数与内容完整性。
   - **输出指标**：输出三项事务的算术平均值 **`composite_tps`（综合平均事务 TPS）** 作为主指标，同时保留 `insert_tps`、`update_tps`、`delete_tps` 明细。

### Web 竖屏信息流与高清大图解码（`web-daily-v1`）

Web 测试在独立的 `:web` 进程中启动**竖屏全屏**系统 WebView，还原老款手机最典型的竖屏刷信息流、列表交互、长文阅读与高清图片浏览场景。测试内容完全离线打包（生成配方见 [`web-assets.gradle.kts`](../app/web-assets.gradle.kts)，哈希锁定见 [`web-corpus-lock.json`](../app/web-corpus-lock.json)）。

每轮测试前先对 4 个分项各执行 1 个单元的预热、校验与复位，随后各执行 **20 个正式工作单元**（每轮共 80 个单元，连续测 3 轮取中位数）：

| 分项 | 单个工作单元操作 | 每轮累计工作量（20 单元） |
|---|---|---|
| 信息流卡片（`page`） | 清空后构建 32 张竖屏单列图文信息流卡片（含缩略图、标题、正文、操作栏），计算样式并强制读取布局高度 | **640 张图文卡片** / 5120 个 DOM 节点 |
| 动态列表交互（`todo`） | 渲染 100 条动态交互列表，切换前 50 条状态；依次按 all / active / completed / all 四次过滤并强制重排；清空列表 | **2000 条列表项**、切换 1000 次、过滤 80 次 |
| 长文段落排版（`text`） | 渲染 24 段长文（每段 256 字符）；替换 48 处短语、高亮 240 个关键词；折叠并展开前 12 段；恢复原状 | **480 段长文**、替换 960 处、高亮 4800 处 |
| 高清大图解码（`image`） | 按序轮询加载 480p（`854×480`）、720p（`1280×720`）、1080p（`1920×1080`）的 JPEG 与 PNG 共 6 张高清素材，在 `<canvas>` 上按原始全分辨率执行 `drawImage` 光栅化解码，抽样读取左/中/右三点 `getImageData` 像素校验，并立即释放画布缓冲防 OOM | **20 次 480p/720p/1080p 全尺寸大图解码与光栅化** |

- **收敛输出指标**：
  - `total_ms`：**Web 综合总耗时**（`feed_ms + image_ms`，越低越好）
  - `feed_ms`：**竖屏信息流耗时**（`page_ms + todo_ms + text_ms`）
  - `image_ms`：**高清大图解码耗时**（20 单元 480p/720p/1080p 大图解码总耗时）
  - 以及子项明细 `page_ms`、`todo_ms`、`text_ms`。
- **视口与超时保护**：页面采用 `width=device-width` 竖屏单列流式布局（字号 12 CSS px、行高 18 CSS px、文本缩放 100%），强制校验 `viewport_height >= viewport_width`。主进程设有硬性超时限制（单轮启动/预热 15 秒、单项测试 20 秒、整阶段上限 330 秒），即使页面脚本卡死也可安全取消并回收子进程。

### 视频解码与播放（`video-decode-v1`）

视频测试包含 7 段固定素材（均为 30 fps、8-bit YUV420、无音轨），具体编码参数与文件 SHA-256 记录在[固定素材清单](../app/src/main/assets/media/manifest.json)中，素材署名见[许可与分发](licenses.md)。

| 素材 ID | 编码规格 | 分辨率 | 时长 / 帧数 |
|---|---|---|---|
| `h263-240p` | H.263 | 352×288 | 1 秒 / 30 帧（兼容性探针） |
| `mpeg4-360p` | MPEG-4 Part 2 | 640×360 | 5 秒 / 150 帧 |
| `h264-480p` | H.264 Baseline | 854×480 | 5 秒 / 150 帧 |
| `h264-720p` | H.264 Main | 1280×720 | 5 秒 / 150 帧 |
| `vp8-720p` | VP8 | 1280×720 | 5 秒 / 150 帧 |
| `vp9-720p` | VP9 | 1280×720 | 5 秒 / 150 帧 |
| `h264-1080p` | H.264 High（含 CABAC / B 帧） | 1920×1080 | 5 秒 / 150 帧 |

每段素材依次通过三条独立路径进行测试，各路径分别记录完成状态（成功、不支持、失败或超时）：

1. **软件解码吞吐**：基于内置 FFmpeg 4.4.6 标量解码器，不按播放帧率节流，解码输出完整 YUV420 帧并使用 `libavutil/sha.h` 校验首帧 SHA-256 哈希。
2. **系统解码吞吐**（API 16+）：通过同步 `MediaCodec` 按规则选择系统解码器（主解码器失败时支持回退一次），检查输出尺寸、PTS、EOS，并对可读的线性颜色布局抽样检查亮度数据。
3. **实时播放**：按 PTS 时间戳节奏向 `Surface` 提交画面，记录解码与提交帧数以及是否达到实时帧率。API 8–15 设备通过 `MediaPlayer` 执行此路径。

### GPU 跨代双场景与填充率（OpenGL ES 2.0）

针对 2010–2016 年间老设备 GPU 性能跨度极大（从 Adreno 200 / SGX530 到 Adreno 330 / Mali-T628 / Tegra K1）的特点，保留两个不同压力梯度的完整场景与纹理填充率测试：

- **Egypt HD（中压场景，113 秒）** 与 **T-Rex（高压场景，56 秒）**：各包含 **1080p 离屏（Offscreen）** 与 **实际窗口分辨率屏上（Onscreen）** 两个阶段。离屏反映 GPU 纯粹跨代硬算力，屏上反映配合物理屏幕分辨率（如 480p vs 720p vs 1080p）与 VSync 的真实游戏流畅度。
- **Fill 纹理填充率（60 秒）**：固定 1080p 离屏四层多纹理混合，直测像素管线与显存带宽瓶颈（`MTexels/s`）。
- **报告一屏成对展示**：在测试报告总览的「核心指标速览」卡片中，Egypt HD 与 T-Rex 的离屏与屏上 FPS 同行成对展示（`离屏 xx.x FPS · 屏上 xx.x FPS`），无需在多张卡片间来回翻找。

## 结果保存与环境监测

测试报告采用分级 JSON 结构：会话级报告记录会话 ID、构建标识、起止时间、整体状态与各阶段结果列表；阶段级报告保存每轮原始样本、配置参数、原生库/ABI 信息及运行环境数据。对于 3 轮制的测试阶段，当 3 轮全部完成且运行参数一致时自动计算有效中位数。

| 状态值 | 含义说明 |
|---|---|
| `completed` | 阶段内所有测试项目正常完成 |
| `partial` | 部分子路径已完成并保留有效结果，部分路径不支持或失败 |
| `unsupported` | 当前设备或系统版本不支持该测试能力 |
| `skipped` | 运行前环境条件（如内存、存储空间）不满足，跳过执行并记录原因 |
| `failed` / `timeout` | 执行或数据校验失败 / 超出规定时限 |
| `cancelled` / `interrupted` | 用户主动取消 / 因切后台、锁屏、窗口丢失或进程重启而中断 |
