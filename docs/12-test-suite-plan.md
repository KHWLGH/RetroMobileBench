# 12 测试套件收敛与媒体解码实施计划

日期：2026-11-13；实施更新：2026-11-14。状态：fixed-suite-v2已实现，自动三轮、Fill与固定24MiB Triad已通过构建、模拟器回归和完整一键流程，真机发布验收尚未完成；范围按本文冻结。代码变更、已通过检查与尚缺的真机证据统一见 [13 实施记录](13-suite-implementation.md)。已纳入 GFXBench 3.0 底层测试复核、屏上 GPU 测试和温升统计调整。

本计划汇总本轮讨论，作为下一轮实现的范围依据。旧文档保留现状记录；其中与本计划冲突的选项、工具链描述和里程碑，在实施时统一更新，不再分别发展多套方案。

## 1. 目标与边界

做一个面向老安卓设备的“一键测完”工具：用户点击开始，程序自动准备资源、执行固定测试、处理不支持的项目并生成一份结果。测试覆盖整数、浮点、压缩、加密、图片解码、视频软解与系统解码、内存、存储和代表性 GPU 场景。

- 用户不选择分类、单项、分辨率、线程数或软硬解模式，也不选择 lite/full 数据包。子测试存在于内部和结果详情中，不扩展成一排操作入口。
- 每次一键执行固定14阶段；CoreMark、SciMark、zlib、加密、图片、内存、文件存储和SQLite各连续三轮取中位数，轮间1秒、末尾不空等。视频固定矩阵及每个GPU模式一次；不让用户选择轮数，不扫描1/2/4/8线程。
- 本轮新增重点是加密、JPEG/PNG 解码，以及包含 HD、Full HD 和系统解码的视频测试。图片/视频编码、音频、4K、HEVC、VP9、AV1 不进入本轮范围。
- 网络测试、联网榜单、续航与长时间压力测试不进入本轮；不以“高级模式”保留一批低优先级测试。
- 首版报告实际速度、覆盖情况和异常原因，不先造一个未经基准机校准的总分。不同协议、分辨率和实现的成绩不能直接混算。

当前实际兼容基线是 **minSdk 8 / Android 2.2**；ARMv7 分 NEON、无 NEON 两套，x86 基线 API 9。原生编译使用 **NDK r10e / GCC 4.9 / gnustl_static**，Gradle 中的 r23c 只用于现代打包工具链的相关环节。旧文档中的“minSdk 16 + r23c 编译全部原生代码”不能继续作为新增组件的兼容依据。

## 2. 固定套件与删减决定

下表是内部测试清单，不是界面上的分类菜单。

| 内容 | 本轮决定 | 内部测试与主要输出 |
|---|---|---|
| CPU 整数 | 保留 CoreMark | 单线程 + N 线程；iterations/s、校验和编译信息 |
| CPU 浮点 | 保留 SciMark small | FFT、SOR、Monte Carlo、稀疏矩阵、LU；各项 MFLOPS |
| 压缩 | 保留 zlib；Zstd 退出正式套件 | 固定语料的压缩/解压，单线程 + N 个独立流；MB/s |
| 加密 | 新增 AES-128-GCM、SHA-256 | GCM 加密/解密含认证，SHA-256 摘要；单线程 + N 线程吞吐 |
| 图片 | 新增 JPEG、PNG 解码 | 固定图片集、固定输出像素格式；MPix/s 与 ms/张 |
| 视频 | 新增完整固定矩阵 | 软件吞吐、指定系统解码器实测、实时播放与正确性；详见第 4 节 |
| 内存 | 复制、填充、依赖访问延迟，恢复STREAM Triad并入同一阶段 | 单线程+N；三数组总工作集固定24MiB；固定工作集变体MB/s，含缓存影响 |
| 存储 | 保留内部存储顺序/随机读写及现有 SQLite TPS | MB/s、IOPS、TPS；SQLite 并入存储详情，不单设入口 |
| GPU | Egypt HD、T-Rex两个完整ES2场景各跑屏上/离屏，恢复Fill离屏 | 固定ETC1；离屏1080p、屏上实际尺寸；场景frames/FPS，Fill为MTexels/s |
| 网络 | 删除本轮候选 | 不实现、不添加入口或依赖 |

从候选表删除 **LZMA SDK、multichase、完整 SQLite speedtest1**。当前 SQLite 的固定事务测试已经存在，与完整 speedtest1 不是同一个项目。

**恢复Fill离屏，ALU、Driver Overhead、Blending仍退出正式流程**，不转成用户可选项目。仅恢复STREAM Triad到内存阶段，不恢复其四内核扫描。现有Zstd、STREAM和GPU底层旧记录仍须可读；实现时移除产品入口和不再需要的发布内容，开发诊断代码是否保留由依赖关系决定。

### 2.1 GFXBench 3.0 的底层测试：正式项目与默认选择要分开看

2014 年的 GFXBench 3.0 评测完整列出了 **ALU、Alpha Blending、Driver Overhead、Fill** 四种底层测试；它们属于正式性能套件，不是后续临时增加的隐藏诊断功能。该版本的高层场景为 Manhattan 与 T-Rex，Egypt HD 已退出当时的新机套件；本项目保留 Egypt HD 是为了覆盖更老的 ES2 设备。

可核对的选择机制如下：

- 当前开源宿主的 `TestRepository::createTestItems()` 默认选中所有不要求 `runalone` 的测试，底层项目没有单独的“默认关闭”例外。`startSession()` 可以运行全部可用项目，也可以运行已选项目；单元测试验证了底层组和单项可以取消选择。电池测试等要求单独运行的项目不在普通全跑列表中。
- 2014 年的 GFXBench 3.0 Windows Phone 实测报道明确描述了“选择测试或全部运行”的界面。它证明当时产品具有选择机制，不能直接证明 Android 每个 3.0 发行包首次启动时的勾选状态。
- 本轮没有复现 2014 年 Android 3.0 APK 的初始界面，因此不把后续开源宿主的默认值说成所有历史发行包的确定事实。可靠结论是：**底层测试是常规正式项目，允许选择；现有开源实现默认包含普通底层项目，不能以“当年只是额外可选项”为删除理由。**
- 仓库中的 `testlist_3.0.json` 在现有宿主里按图形 API 能力选用，`testlist_2.0.json` 是 ES2 路径的列表，文件名不是一份未经变化的 2014 年产品版本快照。历史行为需结合当年资料判断。

### 2.2 四项底层测试的保留价值与本项目决定

| 项目 | 独立价值 | 一键套件的决定 |
|---|---|---|
| ALU | 观察特定复杂像素着色器负载，不等于 GPU 峰值 GFLOPS | 退出正式流程；两个完整场景保留着色器参与的综合负载 |
| Fill | 单独观察纹理填充吞吐，GLBenchmark 2.7时代已有独立Fill；不等同显存峰值带宽 | 恢复1080p离屏60秒，MTexels/s；保留完整自适应负载过程 |
| Driver Overhead | 观察 CPU/驱动处理绘制调用、状态切换的开销 | 退出正式流程；不将其解释成纯 GPU 算力，也不把 CPU 测试当作等价替代 |
| Alpha Blending | 单独观察透明层叠加吞吐 | 退出正式流程；接受首版不隔离透明混合瓶颈的取舍 |

本轮恢复Fill，用60秒补足独立纹理填充吞吐。其余三项仍只保留必要开发回归，不增加高级菜单；完整恢复四项会多240秒，当前只增加60秒。CPU已有整数/浮点/压缩/加密，不再补相似算法；内存补Triad是为了观察多线程数据流，合并进已有阶段，不增加用户入口。网络、编码、完整缓存扫描与完整SQLite speedtest1继续删除。

### 2.3 两个场景，屏上与离屏自动执行

GLBenchmark 2.7 时代的 Egypt HD 与 T-Rex 覆盖不同复杂度的完整场景。固定执行下表五项，用户无需选择模式：

| 顺序 | 场景与模式 | 渲染目标 | 当前配置时长 |
|---|---|---|---|
| 1 | Egypt HD 离屏 | 1920×1080 FBO | 113 秒 |
| 2 | Egypt HD 屏上 | 实际窗口渲染分辨率 | 113 秒 |
| 3 | T-Rex 离屏 | 1920×1080 FBO | 56 秒 |
| 4 | T-Rex 屏上 | 实际窗口渲染分辨率 | 56 秒 |
| 5 | Fill 离屏 | 1920×1080 FBO | 60 秒 |

- 四个场景模式和Fill均保留完整时长，合计 **398秒（6分38秒）**，不含准备、加载、进程启动和阶段间休息。Fill只运行一次，不随CPU项目重复三轮。
- 离屏用于固定分辨率下的比较；屏上用于观察设备在自身屏幕负载下的表现。两种结果分别展示，不混算一个 FPS。不同屏上分辨率的设备不按该数值直接排 GPU 算力高低。
- 屏上必须创建实际窗口的 EGLSurface、向窗口提交帧；把离屏纹理显示在界面上不能冒充屏上测试。采用固定横屏和一致的显示区域规则，记录 EGLSurface 实际尺寸、屏幕刷新率、交换间隔请求及可取得的驱动信息；保持系统正常呈现行为，说明 VSync/刷新率对结果的限制，不把提交帧数冒充精确的实际显示帧数。
- 屏上与离屏各使用独立协议标识，记录顺序和起止温度。不在中间根据温度等待冷却；这些成绩表示固定顺序下的结果，不宣称每项均为冷机峰值。
- 当前代码来自 GFXBench 4.0 的 ES2 路径，并非原版 GLBenchmark 2.7/3.0；使用自己的协议标识，不承诺和历史官方分数等价，也不以“与旧分数误差 ±10%”作为移植验收。
- Egypt 的计算负载较轻，但其素材并不更小。两个场景的资源仍为百 MB 量级，需实测安装体积、解包峰值和运行内存。
- 复核现有场景 192 MiB 空闲内存门槛，依据真机峰值调整，不能凭感觉降低。无法创建固定分辨率目标或内存不足时给出明确状态，不静默降到低分辨率，也不记零分。

## 3. CPU、多核、加密与图片

### 3.1 单线程 + N 线程，覆盖 8 核

CoreMark、zlib 和新增加密项采用同一规则：测单线程，再以设备可用拓扑确定的 N 个工作线程测并行。单核设备不重复执行另一遍“并行 1 线程”。SciMark 保留现有单线程五内核，不扩展线程档位。

N 综合已配置/实际存在的 CPU、在线状态及运行时报告确定。不能只看启动瞬间的 `availableProcessors()` 或 online 掩码，否则老设备的热插拔机制可能把多核识别为单核；也不能盲信内核的最大 possible 编号。记录数据来源、选定线程数和运行前后在线核心状态，交给系统调度，不要求 root、绑核或修改调频器。

实施时统一处理以下限制，不能只改 Java 的一个数字，更不能把硬编码 4 改成硬编码 8 就结束：

- `BenchmarkSuite.parameter()` 中最多 4 线程的截断。
- `native/src/cpu_bench.c` 的 `MAX_THREADS`、线程容器、参数校验和每线程内存分配。
- `native/src/coremark_port/core_portme.h` 的 `MULTITHREAD`，以及 `core_portme.c` 的线程上限和启动/回收逻辑。
- 移出正式套件的 STREAM 仍有固定四线程数组；若保留为开发工具，必须显式拒绝超限输入，不能被共用的新 N 参数越界调用。

内部容量与资源保护须一致、可检查；不能静默少开线程后仍宣称测了全部核心。8 核真机必须实际启动并完成 8 个工作线程；同时区分“配置了 8 个工作线程”和“8 个物理核同时执行”。早期 big.LITTLE 的调度能力可能不同，不能仅靠产品宣传的核数推断。

CoreMark 保持上游核心源码和校验要求，正式阶段不低于 10 秒；缩短全套时间应靠删重复项目，不破坏其计时规则。改变并行策略和参数含义时升级协议，保留旧记录解释。

### 3.2 内存Triad与自动多轮

内存沿用8MiB复制/填充和4MiB依赖链；增加STREAM `a=b+3*c` 内核，double数组各8MiB，总24MiB。1线程和N线程共享同一总量，按64字节边界划分互不重叠区间，统一起点与截止；每项至少1.5秒，用实际元素数×24字节/总墙钟秒数/1e6计算MB/s。初始化/预热/全量校验在计时外，线程创建失败与取消必须回收已创建线程并释放内存。复制/依赖链与Triad工作区不重叠分配。

这是固定工作集STREAM变体，不是标准STREAM成绩，也不保证纯DRAM。官方STREAM针对缓存容量的数组大小要求不适合直接压到所有老设备，本项目保留固定可追溯参数并明确缓存影响，不做缓存层级扫描。完整旧STREAM四内核仅保留诊断接口及历史解释。

八个需采样阶段连续三轮，各轮使用相同正式参数；CoreMark也三轮，双种子和每正式阶段至少10秒不缩短。只有全部完成、构建/协议/参数一致才汇总中位数；图片按六个素材ID、文件与参考像素哈希、尺寸、格式及库匹配，分别汇总MPix/s与ms/张，保留全部原始轮次。每轮完成写会话active_report检查点，中断保留样本且不补零或给正常中位数。

会话升级fixed-suite-v2，内存升级memory-tiny-v2；旧fixed-suite-v1/memory-tiny-v1继续显示。单核省去重复并行阶段。

### 3.3 加密

采用固定版本、最小配置的 Mbed TLS 库接口，自写计时外壳，不直接运行使用全进程信号计时的 benchmark 程序。先验证 r10e、API 8 和无 NEON 构建，再锁定版本。

仅做 AES-128-GCM 加密/解密和 SHA-256。固定缓冲区及消息长度，每线程使用独立上下文，GCM 包含标签生成与验证；已知向量、失败标签验证和回读检查放在正式计时外。不扩展 RSA、ECC、TLS 握手或系统密钥库测试，避免把系统服务差异混入本轮 CPU 加密负载。

### 3.4 图片

JPEG 采用固定版本 libjpeg-turbo，PNG 采用固定版本 libpng，走一致的软件解码路径，不使用各 ROM 不同版本的系统图片库计分。新库同样先通过旧工具链和无 NEON 兼容验证。

使用少量固定图片覆盖照片、带透明通道的界面图和细节复杂图片，以 480p、720p、1080p 量级覆盖常见尺寸。测试前载入压缩数据并准备可复用输出缓冲区，统一输出格式；正式计时包含真实像素解码，不包含磁盘读取。尺寸、像素校验、色彩处理规则和素材哈希进入协议。

首轮只测解码，不新增图片编码、缩放、滤镜和大批格式兼容项目，也不建立重复的线程扫描。

## 4. 视频解码：首轮覆盖 SD、HD、Full HD 与系统路径

“做全”的含义是：同一版本内同时交付固定软件路径、可实际运行的系统路径、HD/Full HD 档位和正确性检查。不是先发布一个仅测 480p 软解的版本，也不是遍历所有解码器和任意格式。

### 4.1 固定素材矩阵

使用同一开放授权视频源制作短片，建议以 Sintel 为源。主矩阵均为 8-bit、4:2:0、30 fps、无音轨，短片初始目标约 4 秒。

| 档位 | 首轮固定码流 |
|---|---|
| SD | H.264 Baseline，854×480，30 fps |
| HD 基础 | H.264 Baseline，1280×720，30 fps |
| HD 复杂 | H.264 High，1280×720，30 fps，包含 CABAC / B 帧 |
| Full HD | H.264 High，1920×1080，30 fps |

另加 H.263、MPEG-4 Part 2、VP8 的短兼容片段，只报告支持与正确性，不再衍生整套分辨率或线程矩阵。这些片段必须符合各格式合法的尺寸和 profile/level 限制。

上述表格冻结产品覆盖范围。具体 level、码率、GOP、参考帧数和编码参数在第一里程碑生成并验证后冻结，写入素材清单、SHA-256 和协议版本；不能只写“支持 720p”而忽略 profile。高负载片段失败不代表该设备所有同分辨率视频都不能播放。

### 4.2 每档自动执行什么

1. **软件吞吐**：固定软件解码器，关闭实时节流，真实生成完整有效帧，报告 fps、实际帧数及线程数；不以解析文件头代替解码。慢设备按固定时间窗结束，不等待其解完整段 HD 视频。
2. **系统解码吞吐**：按固定规则选定并记录解码器名称，实际配置、送入数据并取出输出；能力声明只作预检，不能代替实测。默认只测选定主路径，失败时最多再试一个确定性候选，不穷举全部解码器；系统软解兜底单独标识。
3. **实时播放与正确性**：按时间戳播放短片，检查输出数量、尺寸、时间戳和可取得的抽样画面。分别报告解码吞吐与播放结果，不把输出 fps 等同于真正显示 fps。

软件及系统吞吐窗口初始按每路径 2–3 秒设计，片段、配置、首帧、运行与清理均设置独立超时。视频模块以约 90 秒为正常参考设备的初始预算；在真实老设备上校准后冻结正式参数，不以无设备验证的数字承诺完成时间。

缺解码器、配置失败、输出损坏、超时、完成但低于实时速度要分开记录。前一档失败不自动跳过所有更高档；没有硬件解码时仍可保留软件结果。不能读取的画质/显示丢帧指标标为不可获得，不能补一个估算值冒充实测。

### 4.3 老安卓的硬件识别边界

| 系统版本 | 实现路径 | 能报告的证据 |
|---|---|---|
| API 8–15 | 固定软件解码 + MediaPlayer 系统播放 | 软件吞吐、系统播放是否成功；公共 API 不能普遍枚举/指定底层解码器，硬件类型标记为未确认 |
| API 16–28 | Java 同步 MediaCodec，枚举并按名称创建、实测 | 解码器名称、能力声明、实际输出和性能；名称可识别已知软件实现，厂商名称只能作为线索，保留未知类型 |
| API 29+ | 同上，增加硬件/软件属性 | 记录 `isHardwareAccelerated()` / `isSoftwareOnly()` 的系统声明及实测结果；该属性由厂商提供，不是独立硬件证明 |

不以 MediaPlayer 播放成功或 `createDecoderByType()` 成功直接宣布“硬解支持”。API 16 路径使用旧同步接口并隔离新 API 引用，不依赖 API 21 才有的 NDK MediaCodec，也不让 API 8 启动时加载含新系统类型的实现类。

### 4.4 复用项目和接入方式

- **固定版本、裁剪后的 FFmpeg**：承担 H.264、H.263、MPEG-4 Part 2、VP8 软件解码及必要解封装，裁掉编码、网络和无关组件。明确记录线程设置；帧/切片并行是否有效取决于码流，不能承诺每个视频都用满 8 核。
- **AOSP CTS、Bigflake、Grafika**：参考命名解码器实测、Surface 输出和画面抽查方法，不原样引入重型测试环境。Grafika 的 API 18 基线不能直接当 API 16/8 的实现。
- **ijkplayer**：参考 r10e 构建和老设备兼容处理，不为跑分嵌入完整播放器。其 API 9 基线不能证明 API 8 已可用。

FFmpeg 引入 LGPL 义务，与现有“优先宽松许可证、单 .so 静态合并”的路线存在差异。本计划采用禁用 GPL/nonfree 组件的最小配置，优先独立共享库接入；在锁定构建前落实源码、修改、构建和可替换/重链接材料的交付方式，并更新许可证文档。不能只凭“动态链接”认定全部分发条件已经满足。API 8 构建与许可证交付均列为首个里程碑的验证项，不把未验证组件写成已支持。

## 5. 一键流程与现有问题修正

### 5.1 用户只经历一条流程

**开始 → 自动准备和检查 → CPU/加密 → 图片/视频 → 内存 → 存储（含 SQLite）→ GPU → 本次结果。**

用户只需要开始、运行中的取消，以及完成后的查看/导出。历史记录、设备信息和许可证为辅助页面，不构成另一套跑分配置。运行页显示当前阶段、已完成项目和明确的取消状态，不要求理解内部算法名才能继续。

固定顺序写入套件版本。串行执行，不让 CPU、存储、GPU 和视频互相争抢资源。维持应用级运行状态及检查点；普通界面重建不启动第二份测试。需要画面输出的阶段必须保持前台，切后台、锁屏或输出 Surface 丢失时停止受影响计时，记为中断，保留之前完成的项目。

### 5.2 资源自动准备

正式分发采用一套包含固定必需素材的离线包，首次运行自动校验并准备。取消产品侧的数据包导入和 full/lite 选择；开发构建参数可留在开发流程中。

安装前后空间、解包暂存峰值、哈希、原子替换、失败清理和取消均要验证。准备过程显示进度并有独立超时，不能只把 GPU 调用计时设为 240 秒，却允许之前的解包无限等待。空间不足应说明原因并给出可导出的部分结果，不能让用户猜应补哪个资源包。

这个决定接受正式包较大的代价，换取离线、一键和固定素材。若真机证明无法安装或容纳，必须在发布前重新审查资源方案，不能默默发布一个默认缺场景的“完整测试”。

### 5.3 必须修的流程缺口

| 当前问题 | 实施要求 |
|---|---|
| `startAll()` 遍历全部枚举，结束后显示最近 20 条历史 | 改为固定套件定义和本次会话汇总；完整、部分完成、取消、中断分别呈现 |
| `store.begin()` 失败会阻止测量，`store.save()` 失败会把测量归为失败 | 分离测量状态与持久化状态；保存异常仍保留本次内存结果并允许导出 |
| 未保存结果可能在 busy 状态下无法复制，随后被下一项覆盖 | 整次会话保留结果；结束后的导出包含所有分项、失败项和保存告警 |
| 点击取消没有立即进入清楚的“正在停止”状态 | 立即反馈，阻止启动下一项；在安全边界停止并保留部分数据，说明当前阻塞阶段 |
| CoreMark/同步 I/O 不能随时打断 | 缩小可中断单元；不伪承诺即时停止，不强杀主进程；记录实际停止延迟 |
| 厂商 GPU/媒体组件可能崩溃或卡死 | 保留现有 GPU 独立进程；系统媒体路径采用可回收的独立进程及看门狗，超时后继续后续项 |
| 每项之后固定等 3 秒，包括最后一项 | 仅在阶段间使用固定、可记录的短休息；去掉末尾空等，不称其为充分冷却 |
| 当前共享的 `batteryPreflight()` 会因电池温度 ≥45°C 跳过测试，影响多个套件 | 删除应用层温度拦截、按温度等待及跳过逻辑；温度仅记录，采集规则见下节 |

每份结果包含会话 ID、固定套件版本、测试协议、素材哈希、构建/库版本、实际线程数、运行条件和状态原因。缺项不填零，不支持与运行失败分开；旧版记录继续可读。保持现有存储参数和含缓存回退标记，不顺带增加 SD 卡、多位置或多模式选择。

### 5.4 温度只做升温情况统计

不增加温度设置，也不要求用户先降温。正式流程不因应用读取到某个温度而拒绝开始、暂停等待、跳过、扣分或将有效成绩判为失败；移除当前电池温度 45°C 的门槛。系统自身的降频和保护行为照常生效，若系统导致中断，按实际中断记录。

默认使用现有电池温度来源，记录整次和各阶段的起始温度、结束温度、采样峰值及温升 `结束−开始`，并记录插电状态、时间戳和传感器来源。只增加低频采样，初始按约 2 秒一次设计，不进行高频轮询或要求 root；统计中的“峰值”明确指采样值最大值。温度暂存、采样和导出不能阻塞测量或改变阶段顺序。

结果显示为“电池温度/温升”，不能称 CPU/GPU 结温。缺少温度、读数异常或样本不足时标为不可获得，不填 0，不影响测试继续。若以后记录其它传感器，按来源独立展示，不能把不同传感器的值拼成同一条温度曲线。升温统计用于解释运行条件，不仅凭温升推断已经降频。

## 6. 实施顺序与交付门槛

所有阶段均属于同一轮产品范围；里程碑拆分用于先消除风险，不表示首个媒体版本可以缺少系统解码或 HD。

| 阶段 | 工作 | 完成门槛 |
|---|---|---|
| M1：兼容性与素材验证 | 在真实 r10e 工具链验证加密、JPEG/PNG、裁剪 FFmpeg；生成主视频矩阵；跑通最小系统解码原型；核对 GPU 资源和许可 | 三套原生产物构建通过；API 8/9 加载与无 NEON 要求有证据；API 16 系统解码实际出帧；矩阵参数/哈希/许可冻结，未验证设备明确列出 |
| M2：固定套件与多核 | 删除正式候选和冗余项；替换枚举全跑；统一 1+N 规则与会话结果；完成保存失败处理；温度拦截改为统计 | 单核不重复；8 线程无越界/错误校验；旧记录可读；保存失败后可导出；温度高或缺失均不阻止测试 |
| M3：加密和媒体 | 接入加密、图片与完整视频矩阵；系统媒体进程隔离；实现输出验证、超时和类型标记 | AES/SHA 已知向量、图片像素与视频抽样验证通过；软解/系统解码/实时播放均有结果；720p/1080p 与不支持情形自动处理 |
| M4：GPU 与一键界面 | 两场景各测屏上/离屏，加Fill离屏，共五项；接入窗口 Surface 与 GPU 子进程生命周期；自动准备离线资源，完成取消/中断及整次摘要 | 一键无需选包、模式和子项；屏上真实提交到窗口，离屏固定分辨率正确；两类结果分开；GPU/媒体故障不丢其他成绩；资源或空间不足可结束并解释 |
| M5：真机回归与文档收口 | 兼容、稳定性、时长与峰值内存验证；更新 02–09、11、README、参考资料和许可 | 达到下列验收条件；记录尚未获得的设备验证，不能用模拟器替代硬解/热行为结论 |

保留现有 Framework Instrumentation 和项目测试方式，不为此轮另建测试框架。自动验证重点放在真实风险：8 线程/热插拔识别、保存失败、取消与超时、资源损坏、解码器缺失、错误输出、后台/锁屏、GPU 窗口 Surface 丢失与恢复、温度高值/缺失不拦截、会话汇总和旧记录读取。同步更新目前假定“14 项全部执行”和完整六项 GPU 时长的集成测试。

## 7. 验收标准与发布条件

1. **操作**：从干净安装开始，一次点击可自动走到结果；无分类、线程、软硬解或数据包选择；任何跳过均有原因。
2. **多核**：至少覆盖单/双核、四核、8 核配置；8 核设备实际创建 8 个工作线程并正确回收。记录热插拔造成的在线数变化，不把线程数冒充实际并行核数。
3. **媒体**：四档 H.264 和三种旧格式探测均自动尝试；系统路径实际解码，结果包含解码器证据。API 8–15 不误报确认硬解，API 16–28 保留未知分类，API 29+ 明确属性来自系统声明。
4. **正确性**：加密、图片和视频校验失败不能仍给正常性能成绩；超时或低于实时速度不能笼统显示为格式不支持。
5. **容错**：GPU/媒体崩溃或超时后其余项可继续；取消、空间不足、保存失败或进程重建不会丢掉已有结果，也不会把未完成会话标成完整。
6. **资源**：三套原生产物可加载，无 NEON 设备不会执行 NEON；实际安装、解包和运行峰值经过检查。支持新系统不能以降低当前老系统基线为代价。
7. **时长与 GPU 模式**：两个场景各跑屏上与离屏，加Fill离屏，配置总时长398秒；8个阶段各三轮、视频与各GPU一次。整套预计约12–15分钟，首次准备和慢设备额外耗时需实测，不作为统一保证；最终预算依据真机结果确定。屏上/离屏结果分别包含实际渲染尺寸与呈现条件，Surface 丢失时不继续计正常成绩。
8. **可比性**：协议/素材/线程/读写缓存模式均可追溯；不与原版 GLBenchmark、AnTuTu 等历史总分直接比较，不给缺项填零后算总分。
9. **温升统计**：高温、缺少读数或异常读数不触发应用层停测、跳过或冷却等待；有有效样本时可查看起止温度、采样峰值与温升，来源准确标为电池温度等，不据此自动认定降频。

真机验证至少包含：一台 API 8–15 的 ARM 设备、一台 API 16–18 时代有系统硬解的 ARM 设备、一台可同时调度 8 核的设备，以及无 NEON ARMv7 与 x86 的实际覆盖。设备条件可重叠；API 29+ 属性分支另做验证。模拟器用于功能和异常路径，硬解类型、真实速度、内存峰值及温度行为以真机为准。

主要未决工程风险只保留三类：**新库在 API 8/r10e 下的构建与分发、老系统硬解可观测性、完整 GPU 素材的安装/内存成本**。先在 M1 给出证据，不靠增加用户设置或删除已承诺的视频档位掩盖问题。
