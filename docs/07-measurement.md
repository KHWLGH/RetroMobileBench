# 07 测量方法与老机器上的坑

## 1. 通用规则

| 规则 | 做法 |
|---|---|
| 多次取中位数 | 完整模式下每项跑 3 次取中位数；同时记录最大值和波动范围 |
| 预热 | 正式计时前先跑一小段，让 CPU 升频、缓存热起来 |
| 降温间隔 | 大项之间留降温时间，GPU 测试前等温度回落；记录每项开始时的电池温度 |
| 亮屏 | 测试期间保持亮屏（`FLAG_KEEP_SCREEN_ON`），否则会进入省电状态 |
| 电量 | 电量 ≥ 30% 或在充电；低电量时很多机器会主动降频 |
| 后台 | 提示用户关闭其他应用；测试前记录可用内存 |
| 计时 | 原生代码用 `clock_gettime(CLOCK_MONOTONIC)`；不要用 `gettimeofday`（会被系统时间调整影响） |
| 版本号 | 每个测试都有版本号，参数一改就升版本，旧成绩不再直接比较 |

## 2. CPU

### 2.1 核心热插拔

- 老高通机器有个系统服务 mpdecision，空闲时会关掉部分核心（hotplug），负载上来才逐个打开。三星、NVIDIA 等平台也有类似机制。
- 结果：多核测试一开始只有 1–2 个核在线，分数偏低。
- 应对：
  - 多核测试前先跑几秒满负载预热，等所有核上线。
  - 测试开始和结束时读 `/sys/devices/system/cpu/online`，记录在线核心数；和总核心数不一致就在结果里标注。
  - 没有 root 权限改不了 hotplug 策略，只能记录。

### 2.2 调频与降频

- 记录每个核的 `scaling_governor`、`scaling_cur_freq`、`cpuinfo_max_freq`。
- 发热降频：测试中途频率掉下来，后半段分数会明显变低。完整模式的 3 次重复里如果第 3 次比第 1 次低很多，就提示"可能发生过热降频"。

### 2.3 绑核

- 单核测试可以用 `sched_setaffinity` 绑到某个核（API 16 可用），但大小核设备（4.x 时代较少，例如 Exynos 5410 的 big.LITTLE）绑错核会测到小核。
- 第一版先不绑核，让调度器决定；记录测试期间各核频率即可。

### 2.4 Dalvik / ART

- Android 4.1–4.3 只有 Dalvik，4.4 可以在开发者选项里切 ART。
- 所有测试都在原生代码里跑，不受虚拟机影响。设备信息里记录当前运行时（`System.getProperty("java.vm.version")`：1.x 是 Dalvik，2.x 是 ART）。

## 3. 内存

- tinymembench 的默认缓冲区 32 MB；512 MB 内存的设备上要确认能分配到，失败就缩小并标注。
- 带宽测试结果受 CPU 频率影响很大，同样要预热。
- 延迟测试用随机访问，块越大越能测到主内存延迟；老设备上大块测试很慢，快速模式可以只测到 16 MB。

## 4. 存储

- 读测试必须绕过页缓存，否则测到的是内存速度。API 16 没有 `posix_fadvise`，只能用 `O_DIRECT`（缓冲区和偏移都要按 4 KB 对齐）。
- FUSE 挂载的路径（很多设备的内置"SD 卡"分区）上 `O_DIRECT` 可能返回 `EINVAL`。退回普通读写时，先写一个比可用内存大的文件把缓存挤掉，或者明确标注"含缓存"。
- 闪存的写入性能和剩余空间、碎片程度有关。记录测试时的剩余空间。
- 每次测试用新文件，测完删除；不要在快满的存储上跑。
- eMMC 有写缓存，`O_SYNC` 能保证数据交给存储设备，但不能保证设备内部已落盘，这是所有同类测试的共同局限。

## 5. GPU

### 5.1 离屏 vs 屏上

- 屏上测试受屏幕分辨率和 60 fps 垂直同步上限影响：低分辨率设备分数虚高，高端设备会顶到 60 fps。
- 离屏测试固定 1920×1080 渲染，不同设备可以直接比较。**计分用离屏版**，屏上版只做参考。

### 5.2 计时同步

- OpenGL 是异步执行的，CPU 提交完命令不代表 GPU 画完了。PowerVR、Mali、Adreno 这些分块渲染 GPU 还会把一整帧攒着一起画。
- GFXBench 自己处理了帧同步。我们自己的 GL 代码（例如设备信息采集里的简单渲染）计时时，要在每帧结尾强制同步（`glFinish` 或读回一个像素）。

### 5.3 着色器精度

- Mali-400、Tegra 2/3 的片元着色器不支持 `highp`，见 [04](04-gfxbench-port.md) §4.7。
- 采集设备信息时用 `glGetShaderPrecisionFormat` 查询并记录各精度的实际范围。

### 5.4 驱动问题

- 老 GPU 驱动 bug 多，个别测试可能直接崩溃或画面错误。GPU 测试放在单独进程（见 [01](01-architecture.md) §4.2），崩溃时记录"失败"继续下一项。
- 模拟器的 GPU 是主机 GPU 转译的，成绩没有意义，只能用来验证流程。检测到模拟器（`Build.FINGERPRINT` 含 `generic` 等）时在结果里标注。

### 5.5 内存

- T-Rex、Egypt 配置要求 160 MB 可用内存。512 MB 设备上可能不够，测试前用 `ActivityManager.getMemoryInfo()` 检查。
- KCL 留有低内存通知的 JNI 接口（`assethelper.cpp` 的 `LowMemoryReceived`），宿主可以在 `onLowMemory()` 时调用。低内存时测试可能失败，结果里要能区分"失败"和"跳过"。

## 6. 厂商的跑分优化

- 2013 年 AnandTech 发现三星 Galaxy S4（Exynos 5410 版）检测到特定跑分软件的包名时，把 GPU 锁到更高频率（532 MHz，而普通游戏最高 480 MHz），CPU 也锁最高频。
- 很多厂商当年都有类似的白名单。我们的包名不在任何白名单里，所以成绩可能比当年用 GFXBench、AnTuTu 跑出来的低，但更接近真实水平。
- 对照历史成绩时要记住这一点：差 10–20% 不一定是移植有问题。
